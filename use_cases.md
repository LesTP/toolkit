Eleven project ideas, one anchored on each module. Each is something I think you'd plausibly build — secondary modules in parens.

1. embedding — Clipboard Recall Background daemon that embeds every text snippet you copy (capped at, say, 50 KB each) into a local SQLite + embeddings cache. CLI: recall "that nginx config thing" returns the top-5 snippets by cosine similarity. The cache stays warm across reboots because EmbeddingResult.from_cache is the whole game. (Secondary: none — this is a deliberately leaf-only tool.)

2. clustering — Open-Tabs Topic Map Reads your browser's open-tabs export (probably 200+ tabs if you're like most people), titles + first-paragraph snippets, embeds them, and produces a RAPTOR tree. Output is an HTML page with depth-2 summaries like "Rust async runtimes (12 tabs)" you can collapse/expand. Helps you decide which tabs to close in batches. (Secondary: embedding for vectors, llm_client to power raptor_summarizer.)

3. llm_client — Provider Arena Web UI where you paste a prompt and see Anthropic/OpenAI/Gemini/OpenRouter answers side-by-side, with live token counts and latency. The point is that the unified LLMProvider.call() interface lets you compare without four bespoke clients. Add a "winner" button that logs preferences over time. (Secondary: cost_accountant so the comparison includes price per response.)

4. cost_accountant — Pre-Flight Estimator A meta-style CLI: estimate-llm-job ./prompts/*.txt --model claude-sonnet-4-5. Reads each prompt file, calls estimate_batch() over the lot, shows a table of "biggest 10 calls" and total projected spend, and prompts to abort if it crosses a flag-supplied threshold. Wires the same ledger file across all your LLM-using projects so you get a unified spend view. (Secondary: llm_client for the actual job once approved.)

5. structured_llm — Receipt Filer Forward any receipt image/PDF to it (drop in a folder), it OCRs (out-of-scope, pretend tesseract), then structured_call() extracts to a strict schema {vendor, date, line_items[], total, tax, category} with retry until valid. Writes one JSON per receipt + appends a CSV row. The whole project is "schema + few-shot examples" — almost no glue code. (Secondary: llm_client underneath, cost_accountant because batch-OCRing a tax-year of receipts adds up.)

6. prompt_regression — Prompt CI Hook A git pre-commit hook that detects modified prompts/*.md files and runs the scenarios under prompts/_tests/<prompt_name>/*.json against the new version. Fails the commit if any scenario regresses. The hook is ~30 lines of glue around ScenarioRunner.run_all(). Becomes essential the moment a prompt is tuned by more than one person. (Secondary: llm_client for both the system-under-test and the judge.)

7. telegram_client — On-Call Acknowledger Monitoring systems POST alerts to a tiny FastAPI endpoint; it forwards each as a Telegram message with two inline buttons: "ack 15m" and "ack 1h". A polling loop watches for callback updates and updates the original message to "✅ acked by @you, expires 14:32". Page-then-snooze for solo-oncall sanity. (Secondary: gateway if you ever want to add a second channel like Slack — then this anchor flips and becomes use case 9.)

8. json_rpc — Terminal LSP Companion CLI tool you point at any LSP server binary (pyright, rust-analyzer, etc.) and a source file. It spawns the server via SubprocessTransport, sends initialize + textDocument/didOpen + textDocument/hover for whatever symbol is under your cursor, prints the hover doc. Pure stdio JSON-RPC — exactly what the module was built for. (Secondary: none. WebSocket transport unlocks a v2 that talks to LSP-over-WS dev servers.)

9. gateway — Cross-Platform Pub You write one "post" in a markdown file. The tool publishes it to your Telegram channel, your blog (via Telegraph), and a local JSONL log — all from one OutboundMessage per platform, format-converted automatically. Inbound replies on any channel flow into a unified on_message callback that you can view as a single threaded feed. (Secondary: telegram_client is the adapter; feedback_collector if you want to track which channel engages most per post.)

10. source_ingestion — Personal News River RSS + a Reddit feed of r/MachineLearning + a couple of Telegram channels + a corpus importer for your old LiveJournal archive, all polled on configurable intervals into one ContentItem stream. Render as a single chronological web feed with source badges. Marker store means it survives restarts and laptops sleeping. (Secondary: embedding + clustering to add a "what's everyone talking about today" topic header at the top.)

11. feedback_collector — Self-Pruning Newsletter You write 5–10 candidate "blurbs" per day, each tagged with an intent_tag like funny, technical, meta, personal. A scheduler publishes one per hour via gateway. feedback_collector watches reactions and silence per tag. After ~50 posts it tells you "blurbs tagged meta get 80% silence; consider dropping them" — and optionally auto-stops publishing low-engagement tags. The whole project is essentially an evolutionary filter on your own writing voice. (Secondary: gateway for delivery, plus any memory store satisfying the duck-typed contract.)

Pattern I notice: the modules naturally cluster into three layers — knowledge (embedding, clustering, source_ingestion), LLM plumbing (llm_client, cost_accountant, structured_llm, prompt_regression), and messaging/feedback (telegram_client, json_rpc, gateway, feedback_collector). The most interesting projects are usually the ones that cross two layers (e.g. #2 knowledge + LLM, #9 messaging + feedback). Pure single-layer projects exist (#5, #8) but feel more like utilities than products.
